# ADR-210: Scheduled Host Commands with Explicit Authority and Durable Outcomes

- **Status:** Proposed
- **Date:** 2026-10-23
- **Grounding commit:** `036ac6a04db9ccfa1c712aeb7c83fb93dddfd4c0`; every source reference below is read at this commit.
- **Placement:** Extension design for the schedule, exec, tool and comm packs. The base layer gains only the narrow authority interface named in D10.
- **Depends on:** The shared caller-authority contract in ADR-143; the exec containment and receipt contracts in ADR-181; accepted and implemented authority adapters for the rights introduced here.
- **Amends, when accepted:** ADR-181's materialized-tree-only execution shape, fixed filesystem profile, environment and executable-path restrictions **only for the explicit host profile**; schedule declaration, misfire and occurrence accounting; tool registration pins; comm delivery deduplication. Existing tree execution keeps its contract.
- **Related proposals:** ADR-181 Amendments 13–14, ADR-143 Amendment 3, ADR-207, ADR-208 and ADR-209. Their presence in the tree is not evidence that their proposed functionality is available.

## Requirement this decision serves

Timed and recurring runs move into khive. The local scheduler that carries them today, the lionagi `li schedule` store, is retired for this purpose because any process with shell access can rewrite its store. Runs are declared through the khive schedule pack and charter routines and execute inside the khive computer under khive permissions. This follows the target architecture: khive holds operations, privilege and approval, established routines (charters) and communication; agents run locally on their own runtime; state is distributed and joined through a communication node.

Every decision below is read against one test: each run the local scheduler carries today is declarable in khive when this ADR lands, or this ADR names it as left outside and says why in the same row. The run shapes measured so far:

## Context and teardown

Within the requirement above, the product need is a registered host command scheduled once or repeatedly, with a retained working-directory declaration, an immediate pre-launch hold check, explicit network permission and a durable outcome message. The requirement originates in [issue 5931](https://github.com/ohdearquant/khive/issues/5931), including its recurring-execution comment.

### The strongest alternative: keep networked host execution outside khive

Keep exec restricted to materialized trees. Provision one fixed OS-supervised job, with its own filesystem and credential permissions, and let khive request that job and observe its result. A protected service can keep credentials and its executable manifest beyond the requesting process's write authority. This avoids putting arbitrary host directories, remote effects and credential disclosure into the existing sandbox contract. It also avoids suggesting that a scheduler database becomes protected simply because another process owns its API.

This objection survives in two respects. First, same-user local processes remain one cooperative trust domain: ADR-181's proposed network design explicitly says that same-UID clients can supply another actor label, and that its staged executable is writable by an outside process of the same user (`docs/adr/ADR-181-exec-verb-sandboxed-run.md:1008`, `:1482`). Second, existing Seatbelt execution does not certify that detached descendants have stopped; the accepted ratification retains initial-group cleanup and reserves stronger certification (`docs/adr/ADR-181-exec-verb-sandboxed-run.md:834`). A networked survivor would retain its launch profile's reach (`docs/adr/ADR-181-exec-verb-sandboxed-run.md:1107`). Moving a schedule alone solves neither problem.

The alternative costs a separately deployed executor, a request/result protocol, credential provisioning and reconciliation. A launchd job running as the same user with a mutable script does not supply the stronger boundary. Keeping a second timer also splits occurrence accounting. A fixed supervised **executor**, with khive retaining the only timer and outcome ledger, remains the preferred alternative when protection from same-user processes or certified lifetime containment is required. It is not an already available implementation.

The recommendation below survives only as an explicit **cooperative local host profile**. It provides central admission, filesystem confinement and durable accounting; it does not claim isolation from another unsandboxed process of the same user. Credential-bearing network execution has an owner decision in D4 and remains disabled until that decision is accepted. A requirement for stronger isolation selects the supervised/brokered alternative instead.

## Decision

All wire names, records and behavior introduced below are requirements of this proposal, not claims of existing verbs or fields.

### D1. Exec owns one explicit host profile; schedule remains the timer

Add `mode="host"` to exec's execution contract, mutually exclusive with `tree`. Omission retains the existing tree mode byte-for-byte where its existing contract requires that. A host run names a registered tool, immutable argv/environment declarations, an absolute `run_dir`, and an optional relative `hold_file`. Schedule stores **one** exec action; it does not gain a shell string, chain support or a separate subprocess launcher. The current single-operation refusal remains (`crates/khive-mcp/src/pending_events/drain.rs:796`).

Host mode is explicitly enabled in deployment configuration and requires a host-capable registration plus D5 authority. For this slice, only a scheduler replay carrying an opaque, freshly admitted occurrence context can enter it. Direct calls, fabricated event IDs and nested dispatch that loses the context refuse; supporting an immediate host-run API is a later authority surface, not an implicit bypass.

The exec pack owns preparation, sandbox compilation, launch, output capture, hold checks and execution receipts. It reuses its bounded launch/capture machinery, but never calls tree materialization or captures the entire host directory into `tree_out`. Host receipts state `mode=host`, `tree_in=null`, `tree_out=null`, the directory identity and the effective resource profile. Their null trees are not an empty change set or a claim that no host effects occurred.

An unsupported platform or unqualified backend refuses both host declaration and launch with the missing capability named. No unsandboxed fallback ships. macOS is the initial candidate; the inspected backend requires `/usr/bin/sandbox-exec` (`crates/khive-pack-exec/src/sandbox.rs:37`). Linux support needs its own demonstrated filesystem, network and lifetime boundary, not merely a new spawning branch.

### D2. Freeze intent and directory identity; distinguish live data from executable inputs

A host registration contains a versioned `host_profile`: allowed working-directory roots, read roots, write roots, executable-path exceptions, environment keys, network class, credential disclosures, and resource/output limits. Its entire canonical representation participates in the tool pin. A profile change requires a new approval. Existing registrations without the property keep their old pin representation; absence is not silently rewritten as a new null field.

At declaration, resolve an explicit absolute working directory, record the requested spelling, canonical path and file identity, and bind them into an immutable schedule definition. Resolve neither cwd nor HOME from the declaring session at fire time. At launch, reopen without following substituted components and compare the recorded identity. Missing/replaced/renamed directories refuse with `run_dir_changed` or a named open error; they are not recreated automatically. Keep the directory handle through the pre-launch checks and derive cwd from that handle. The profile's pathname rules must describe that same admitted object. A same-user process racing path changes remains outside the cooperative protection claim.

The snapshot is a snapshot of **configuration and identity**, not a backup of directory contents. Repository/data reads may remain live if the approval says so. The registered entry executable and explicitly declared entry scripts are content-pinned and launched from verified, read-only staging, reusing the network proposal's staging rules where applicable. An interpreter pin alone does not pin its script. Dynamic libraries, subsequently read code and runtime-loaded data remain outside a top-level digest; the declaration must disclose that limit, as ADR-181 already does for networked staging (`docs/adr/ADR-181-exec-verb-sandboxed-run.md:1304`, `:1482`).

The event's host `run_dir` is separate from the private per-occurrence exec artifact/staging directory. The former is retained after execution. The latter holds bounded output and receipt-related artifacts under exec ownership, with disclosed retention; it is not a replacement cwd and is not writable by the child when it contains approved executable bytes.

Allow writes only to the event directory and specifically granted additional roots, including a fresh private scratch directory. Do not grant all of `/tmp`; set `TMPDIR` to the private scratch path and require callers that hardcode shared `/tmp` to adapt. Reject writable roots that overlap authority databases, daemon configuration, executable staging or declared credential sources. Read-only exceptions inside a writable root must be real enforced denials, never annotations.

### D3. Network is absent or explicitly broad outbound; no fictional destination filter

For the initial host profile, recommend the already proposed `network="outbound"` vocabulary, subject to acceptance and implementation of ADR-181 Amendments 13–14 and qualification of the **combined host profile**. With network absent, retain the no-network template. A single side-effect label, a default read allow, or a policy allow does not enable network. A pinned tool grant, D5 authority and host enablement are all required.

This is broad outbound permission. An inventory such as “SSH to one host, HTTPS to github.com” is not an enforced allow-list and must never appear as one in an approval. Requests for enforced `host:port` constraints are refused as `network_policy_unsupported` by this profile. No declaration is accepted on the hope that a later run will obtain permission; unhonored network requirements refuse at declaration and again at fire time.

The cited design reports a Seatbelt IP-filter rule, a resolver Unix-socket allowance and interacting localhost denial, with behavior qualified per OS build. It does **not** establish an enforceable per-hostname contract. A hostname needs a stated resolution time, address set, refresh/rebinding policy and address-family handling; an IP/port check would still not prove an application-layer hostname on shared addresses. None of those properties is supplied by the literal word `egress` (`docs/adr/ADR-181-exec-verb-sandboxed-run.md:923`, `:950`, `:1033`, `:1372`).

Keep the proposed build and measured-loopback checks, staging pins and grant requirements. The broader filesystem/executable host profile needs its own controlled network qualification; an existing tree-profile measurement cannot certify it. Refuse missing policy/configuration, unknown classes, unlisted builds and failed qualification. Do not silently downgrade to offline execution.

The system resolver socket grants more than DNS lookups: the ADR reports service browsing and registration too (`docs/adr/ADR-181-exec-verb-sandboxed-run.md:1270`, `:1470`). Its exposure is part of approval, not hidden infrastructure. The local kkernel socket is a separate capability and is **not** included. Outcome notification moves into the trusted scheduler, removing that socket from the command's needs. A later daemon operation requires an exact, attenuated adapter; access to the ordinary daemon socket is not an acceptable substitute.

### D4. Credential and version-control exceptions are explicit; the owner selects the risk boundary

Retain ADR-181's current git/gh/`git-*` denials for ordinary tree execution and host registrations without an exception. For an explicitly approved host registration, permit only the declared canonical executable paths and required helpers through a separately rendered profile. Keep the operator's `never` set authoritative. No blanket removal of `git-*` denials; the helper closure must be exercised under the actual profile. A wrapper that calls denied paths fails, and a renamed binary is not treated as an approved exception (`crates/khive-pack-exec/src/sandbox.rs:202`; `docs/adr/ADR-181-exec-verb-sandboxed-run.md:419`).

For public remote reads, recommend a fixed git invocation with credential helpers, prompts and ambient global/system configuration disabled. The caller's measured use does not establish that a credential is necessary for a public read. `gh`, its token store, the user's whole home and an inherited credential-helper environment remain unavailable. If authenticated HTTPS is actually needed, declare it as a new credential-use requirement rather than granting home access to make a helper succeed.

An SSH private-key file is a credential disclosure, not an ordinary toolchain read. A grant that allows a command to read it and use broad outbound network permits that command to copy the key to any reachable peer. An endpoint restriction would still allow disclosure to an allowed peer; an ssh-agent socket would expose signing operations, not merely file reads. Revoking the schedule does not revoke a copied key. This follows the distinction between credential use and raw export in `docs/adr/ADR-209-root-policy-overrides-and-flow-history.md:329`.

**Owner decision, not implied by this ADR:**

1. Accept cooperative local raw credential disclosure plus broad outbound reach and uncertified descendant lifetime. Each approval names exact credential files and destinations of notifications, acknowledges that read bytes can leave, and accepts the post-admission revocation limit. Only exact key/known_hosts paths are added; no home subtree or ambient agent socket. HOME remains private, with explicit SSH identity and known-host options.
2. Require credential custody outside the child and a separately specified fixed-operation broker/supervised executor, optionally with enforced destination filtering or a stronger lifetime backend. The service performs the approved remote operation without exporting its credential. It requires additional implementation and qualification before this caller migrates.

**Recommendation:** choose option 2 for credential-bearing recurring commands. Option 1 is a consciously broader product profile and needs explicit owner acceptance before implementation of its credential exception. Do not block credential-free scheduling/notification work on that strategic choice, and do not claim the existing SSH caller is supported before one complete route passes acceptance.

### D5. Reusable declaration authority and fresh per-occurrence admission

Use one shared caller-authority service. Introduce a constrained reusable `ScheduledHostCommand` right through that service, with exact structural grantee, immutable schedule-definition digest, tool/profile pin, filesystem/credential/network envelope, validity interval and immutable lineage. Its administration requires authority over the complete constrained right. It is not a tool grant, a `RecordObservation` grant, a free-text scope or an indefinitely reusable ADR-209 single-use approval. ADR-143's minimum proposed profile currently supports observation rights, so this is an explicit addition with its own activation tests (`docs/adr/ADR-143-store-held-caller-grants.md:665`, `:691`; `docs/adr/ADR-193-charter-runs.md:608`; `docs/adr/ADR-209-root-policy-overrides-and-flow-history.md:220`).

Declaration requires non-anonymous attributed/authenticated ingress appropriate to the selected deployment profile, current Gate admission, current tool allow **from a pin-matching grant**, the exact standing right and successful host-capability validation. `ask`, `deny`, missing/unreadable authority and unsupported profiles refuse declaration with structured reasons. They create no runnable event. Approval can be requested separately and the declaration retried; the scheduler never asks a human at fire time.

Bind the event to the verified declarer and captured grant references through immutable pack-owned provenance. Refs are lookup keys, never lasting permission. Each occurrence re-admits that declarer through the same service, checking expiry, terminal lineage, current actor state, profile/definition digests, Gate and tool policy. An occurrence is not a new privileged principal and inherits no daemon authority. A charter may supply workflow evidence in addition; it creates no authority and is not a prerequisite for every schedule. These distinctions follow ADR-193 D9 and ADR-207's deferred-effect contract (`docs/adr/ADR-193-charter-runs.md:176`; `docs/adr/ADR-207-runtime-actor-registry.md:322`).

At the final pre-spawn seam, serialize a fresh authority decision and durable launch intent under an occurrence claim. Revocation committed before this admission refuses launch; revocation committed after it does not retroactively undo admission or terminate descendants. Filesystem checks and process creation are outside the database transaction, so neither an atomic hold/spawn claim nor an atomic database/process effect is made. Unreadable or changed dependencies before spawn abort the attempt.

Do not reinterpret tool-policy precedence: a new `tool.policy` deny does not defeat an already active tool grant in the current implementation (`crates/khive-pack-tool/src/policy.rs:880`). Stop future admission by revoking the exact standing right or tool grant, or disabling the host profile. The independent shared-authority denial cannot be overridden by a tool allow.

Changing command, args, effective env, directory, hold path, recurrence, lateness, credentials or recipient creates a new definition and requires authority covering it. Generic note edits cannot rewrite executable intent. Existing schedule provenance already separates creator authority from editable note metadata (`crates/khive-mcp/src/pending_events/drain.rs:407`).

### D6. Hold is a pre-launch observation, not a lock or cancellation channel

`hold_file` is a normalized nonempty path relative to the pinned host directory, with no absolute or parent component. Resolve parent components without following links and check the final entry without following it. Any existing final directory entry holds the occurrence: regular file, directory, symlink including a dangling link, FIFO or device. Only an observed absent final entry under verified readable parents permits progress. Missing/unreadable parents, permission failures and other lookup errors produce `hold_check_failed`, not absence.

For a regular file, open without following links, compare identity with the checked entry, and collect a bounded prefix as hold text. Default `hold_text_limit_bytes=4096`, configurable and disclosed; read at most the limit plus one byte. Record retained bytes, whether more bytes were observed, encoding, observation time and `capture=complete|incomplete|unavailable`. Unknown full length is null, not a guessed count. Binary text is safely encoded with that encoding named. Read failure produces `hold_read_failed` and no spawn. For nonregular entries record the entry kind and no content; never open a FIFO or follow a symlink to obtain a message.

Perform this check after expensive preparation and immediately before the final admission/deadline/spawn sequence. A file created after the check can lose the race; a file removed after a held observation does not revive that occurrence. Record the check time and the limit. A stronger interlock requires a cooperative lock protocol or broker and is not represented by a filesystem existence check.

`held` consumes the scheduled occurrence and produces its own receipt/notification. Repeats advance normally; removal permits a later occurrence, never a replay of the held one. A command can modify a writable hold path after it starts; this does not turn the file into a running-process kill switch.

### D7. Per-event deadlines have a stated admission boundary

Allow `max_lateness` with `skip`: a representable integer number of seconds greater than or equal to zero. Absence keeps the configured global grace. Preserve `catch_up_once`'s requirement for an explicit positive value. Reject null, wrong types, negative/overflowing values and unknown policies. Today `skip` rejects the argument and catch-up requires positivity (`crates/khive-pack-schedule/src/misfire.rs:20`).

For each occurrence, compute the deadline from its immutable `scheduled_for`. At selection and again after preparation/hold checking, read a fresh clock at the supported timestamp precision. Admit only when `scheduled_for <= decision_at <= scheduled_for + effective_max_lateness`. Equality is allowed; greater is `missed`, with no spawn. Persist both decision times and the effective bound. A clock that cannot be read or whose required ordering cannot be established refuses; a backward step must not replay an occurrence already recorded.

`0` means **no admission observed after the scheduled instant**, with no hidden tick-width allowance or integer-second rounding. It will normally miss on a polling scheduler, including after slow preparation. The polling floor is stated beside it: the daemon tick defaults to 60 seconds and is configurable (`crates/khive-mcp/src/pending_events.rs:554`), so a zero bound admits only an occurrence whose pass reads its clock at the scheduled instant, and is never a real-time start promise. It does not promise physical process start at that instant: the OS can schedule the wrapper or child later. A product requirement for a hard actual-start deadline remains unsupported and must be refused, not described using this weaker guarantee. Increasing timer precision is a separate availability improvement, not permission to start late.

The literal “never late” requirement must be ratified with this boundary. A practical caller may instead choose a small positive explicit bound. Do not silently choose that bound on its behalf.

### D8. Every due occurrence has durable identity, outcome and replay rules

Introduce a version-3 immutable occurrence ledger owned by schedule, separate from the event's mutable next-trigger view. Every record, receipt, launch intent and delivery attempt has an ID. A unique key over store identity, schedule ID, immutable definition revision and canonical UTC `scheduled_for` identifies one occurrence; lease renewal/reclaim never changes that identity. A receipt has its own ID and links any exec receipt. Invocation and notification IDs remain separate.

Persist an occurrence claim before effects. Persist `launch_intent` before entering the process-creation seam. Record terminal outcome once, together with one durable notification intent and the recurrence cursor update in one schedule transaction. If persistence cannot establish a claim or launch intent, do not spawn. A failed terminal write is an unsettled attempt for recovery, not successful finalization.

The outcome vocabulary is `succeeded`, `failed`, `timed_out`, `held`, `missed`, `refused`, `spawn_failed`, `cancelled`, `indeterminate`. Include a structured reason and nullable exit code/signal. A successful dispatch envelope is not command success: inspect the exec domain result, timeout and receipt. Unknown enum values or malformed result shapes become `indeterminate` with original evidence retained; never default to success. Cleanup/quiescence stays separate and preserves ADR-181's uncertified lifetime evidence.

A crash after launch intent can leave it unknown whether a process or remote effect started. Reconcile using the same invocation and exec receipt if possible. Do not repeat an arbitrary host command automatically after uncertainty, timeout, nonzero exit or lease expiry. An exec receipt that is missing is not proof of nonexecution. A repeat with an unresolved prior launch is suspended pending reconciliation; nominal due instants while suspended are still accounted as skipped `refused` occurrences, with a named suspension reason, rather than launched.

If `indeterminate` has already been finalized and notified, later reconciliation appends separately identified evidence and changes the settlement view; it never rewrites that receipt or issues a second terminal-outcome notice. An explicit separately authorized reconciliation notice is a different message kind, outside the one-outcome-notice contract. Resuming a suspended series requires recorded resolution, not a lease timeout or an empty process lookup.

For repeats, enumerate every nominal due instant between the durable cursor and a captured reconciliation horizon. `skip` considers only the original source trigger for launch under its bound. If that trigger is missed, all other instants due at the horizon are accounted as missed too; it does not substitute a newer instant to recover the run. If it is admitted, other due instants are still accounted without launching a burst. `catch_up_once` instead selects at most the latest due instant, records older instants separately as missed with reason `superseded_by_catch_up`, and preserves its bound. A held or finished run never resets the recurrence anchor. Occurrences falling while a direct invocation is active are recorded as skipped `refused` with reason `overlap`; do not run two direct invocations of the same schedule concurrently.

Bound enumeration to 200 occurrences per transaction/pass, disclose the bound and remaining-work cursor, and resume it durably. Do not jump the cursor over unrecorded instants or summarize away their messages. Storage/admission pressure pauses new launches and exposes `accounting_blocked`; it does not delete old outcomes. Clock changes, restart and long runs use the original recurrence definition and monthly anchor. Preserve the existing parser's calendar/interval behavior and UTC cron meaning (`crates/khive-mcp/src/pending_events.rs:40`).

Cancellation stops creation of future nominal occurrences at its recorded cut point; already materialized unsettled occurrences are resolved as cancelled or indeterminate according to whether launch may have happened. It never invents an infinite series of future cancelled notifications. Reconciliation and notification work survive schedule cancellation.

Keep receipt versions 1 and 2 readable under their existing semantics. V1 has no implied per-occurrence historical inventory; V2 names a catch-up selection and source trigger (`crates/khive-mcp/src/pending_events.rs:133`, `:166`). Do not relabel them as v3, backfill invented skipped receipts, or change their occurrence IDs. Enable new host schedules and schedules explicitly requesting the new contract only when all consumers recognize v3. Older stored schedules keep their prior behavior until explicitly replaced/migrated with a recorded cutover; their new owner is not inferred from editable metadata.

### D9. Notification is an idempotent system effect, independent of command success

Host schedule declarations require outcome notification. Omitted `notify` resolves to the verified declarer and is stored explicitly. A different recipient requires an explicit authorized address and disclosure scope at declaration. Freeze the recipient in the definition; changing a caller's default identity or cwd does not retarget delivery. A deployment lacking the required comm capability refuses the declaration.

The sender is a bootstrap-provisioned scheduler service identity, with permission only to deliver recorded schedule outcomes to their bound recipients. It never impersonates the child or uses its ambient daemon credentials. Audit both service sender and original declarer. This narrow delivery authority survives revocation of execution authority so a refused run can still be reported. It confers no general ability to send messages; tombstoned/invalid recipients produce a visible delivery failure, never a substitute destination.

The schedule transaction inserts an outbox item uniquely keyed by `(store_id, occurrence_id, recipient, outcome_notice)`. Comm supplies an internal idempotent delivery contract with that key, immutable payload digest and stored outbound/inbound IDs. A same-key/same-payload retry returns those same IDs; different bytes refuse with conflict. Its recipient insertion/dedup record must be atomic in the comm store. If schedule and comm use separate stores, the outbox retry is still safe because deduplication occurs at the receiving write. This is new required integration, not an assumption that current `comm.send` already offers it.

The guarantee is **one logical internal message per terminal occurrence, eventually, while storage, authorization and the destination are available**. It is not a promise of one external email or exactly-once arbitrary side effects. Crash after comm commit but before outbox acknowledgement must not duplicate the internal message. Cancellation and notification failure must never rerun the command. Notification status is independent: `pending`, `retrying`, `delivered`, `failed`, `unknown`; only a verified recipient commit marks delivered. A timeout/unknown is retried with the same key or reconciled, never treated as delivered.

Use bounded exponential retry (initial 1 second, maximum interval 5 minutes); after 20 consecutive failed attempts retain the item as `failed` for explicit retry with the same key. Unknown delivery remains visibly unresolved until lookup or an idempotent retry establishes it. Expose pending/failed/unknown items in agenda and a paged delivery view, with attempt count, next-attempt time, last error and message IDs. Do not depend on the failing channel to report its own failure. These are proposed operational defaults, not measured delivery guarantees.

Each message carries schedule/occurrence/receipt IDs, scheduled time, outcome/reason, admitted/started/completed times as available, nullable exit code/signal, cleanup qualification and output references. Include separately identified stdout/stderr tails when present. Default notice cap is 8192 bytes per stream, bounded by the retained exec output; disclose configured notice cap, effective exec cap, produced/retained/included bytes, encoding and complete/incomplete/unavailable status. Never imply that the tail is the whole output. The exec contract already distinguishes stream counts and effective caps (`docs/adr/ADR-181-exec-verb-sandboxed-run.md:99`, `:367`). Preserve retrieval of everything actually retained; omitted or unknown historical cap values stay unknown.

Output and hold text are data, not commands or authority. Notification is an approved disclosure to its bound recipient. Do not copy credential values into approvals, argv or provenance; output collection cannot certify that arbitrary child-produced text is secret-free, so credential-disclosure approval must account for the output sink too.

First implement generic v3 accounting, deadlines and delivery as complete independently usable functionality. Next implement the shared right and offline host profile with its full admission/hold/sandbox acceptance. Activate outbound host execution only after ADR-181's network proposals are accepted, their implementation is present, and the combined profile passes its controls. Activate credential use only after D4's owner choice and that route's acceptance. No callable partial host feature advertises support before its obligations hold.

ADR-208 integration is optional: a charter can observe a terminal occurrence through an authorized producer and gate later work. It neither owns the timer nor launches commands (`docs/adr/ADR-208-charter-workflows.md:54`, `:84`). This ADR does not depend on an unavailable ADR-193 Amendment 6.

## Alternatives considered

1. **Fixed OS-supervised executor only.** Stronger candidate when separately protected credentials or lifetime containment are necessary; rejected as the mandatory executor for every credential-free cooperative local task because it adds deployment/protocol overhead. Retained as D4's preferred credential-bearing route. It still needs khive occurrence and notification accounting.
2. **Schedule spawns directly.** Rejected: creates a second sandbox, credential and receipt implementation, and makes scheduler permission imply host execution permission.
3. **Charter-only scheduling.** Rejected: workflow evidence cannot supply execution confinement, and the inspected charter action contract performs no external I/O. It also makes a single timed command depend on workflow machinery.
4. **Host:port lists compiled immediately into Seatbelt.** Rejected for the first profile because the provided evidence does not establish that contract. A separately qualified filtered backend is preferable where narrow egress is mandatory; unsupported constraints must refuse meanwhile.
5. **Global egress flag and inherited HOME.** Rejected: broadens unrelated tools and quietly exports ambient credentials. Explicit per-registration broad outbound is already a material approval and does not justify home access.
6. **Wrapper/rename exceptions.** Rejected: wrapping preserves child-path denials; renaming bypasses a guard without expressing authority. Use explicit resource-profile exceptions or a fixed adapter.
7. **Command followed by `comm.send` in a stored chain.** Rejected: the current single-op contract refuses chains, failure before the send loses notice, and retry can repeat the host effect. Use the outbox.
8. **One series summary for downtime.** Rejected for the requested contract: it hides individual missed occurrences. Bounded durable enumeration pays the storage and message cost openly.

## Rationale

This design separates five facts that otherwise look like one success: the schedule became due, current authority admitted an exact occurrence, the process may have launched, a terminal outcome was recorded, and a notification reached its recipient. Each has its own durable evidence and failure behavior. Exec remains the only host-command implementation; neither a tool label, workflow phase nor scheduler identity creates extra authority.

## Known limits and open decisions

- **Owner ratification required:** cooperative raw-credential/broad-outbound execution versus a protected broker/supervised route; the recommendation is the latter for credential-bearing recurring jobs. The unchanged SSH caller is not yet supported by this proposal alone.
- **Deadline wording required:** the proposed zero-lateness guarantee ends at final admission. If the requirement is actual process start at an exact instant, this backend is insufficient.
- **Containment:** same-user unsandboxed processes, mutable live inputs, external effects and detached descendants remain outside stronger claims. A stored grant and a file digest cannot repair those boundaries.
- **Network qualification:** proposed tree-profile measurements do not establish exact destination filtering or the new combined host profile. No raw-key/outbound path activates on an unmeasured assumption.
- **Historical completeness:** v1/v2 schedules did not record every missed interval; the new ledger cannot recover facts they never persisted.
- **Delivery:** internal idempotent insertion is achievable only with the specified comm integration. External transport exactly-once delivery and delivery during permanent outage are not promised.
- **Dependency status:** ADR-143 Amendment 3 and ADR-181 Amendments 13–14 are Proposed at the grounding ref; ADR-193 Amendment 5 is Accepted, while Amendment 6 is absent there. These are explicit integration gates, not authority supplied by this ADR (`docs/adr/ADR-143-store-held-caller-grants.md:655`; `docs/adr/ADR-181-exec-verb-sandboxed-run.md:1251`; `docs/adr/ADR-193-charter-runs.md:565`).
