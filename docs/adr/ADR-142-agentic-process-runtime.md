# ADR-142: Agentic Process Runtime

- **Status:** Accepted
- **Date:** 2026-08-03

## Context

khive packs contribute vocabulary and handlers, while the runtime composes their contributions into a coherent dispatch surface. [ADR-017:27-40,164-175; ADR-023:65-85]

The warm daemon already owns a long-lived runtime and a `VerbRegistry`, which provides the appropriate execution host for process records that must outlive one model response. [ADR-049:40-55,59-65]

The public session surface stores continuity metadata, including `provider` and `provider_session_id`, and exposes `session.store` and `session.resume`. `session.resume` selects a stored session note by its khive record identifier; `provider_session_id` is an external, provider-native identifier that is not a khive record identifier and is not unique across stored records. [ADR-083:80-99,145-175,199-212]

The comm model already distinguishes an actor identity from a message payload and carries that identity through runtime request context. [ADR-057:120-152; ADR-063:95-132]

On the daemon's native local path, the operating-system peer UID is the authenticated principal, and many actor identities over one socket is the accepted design: the actor label is per-request attribution, not an independently authenticated identity. [ADR-096; `crates/khive-runtime/src/daemon.rs:387-400,417-422` at commit `9442ec2c5`]

An on-device lattice inference seam is an established direction for local inference, although the cited native rerank integration is explicitly deferred rather than evidence that a general agent provider exists today. [ADR-042:18-38,61-71]

Today's runtime composes packs through a registry and accepts per-request identity only at its dispatch boundary; no current source defines a durable agent-process record, a provider abstraction, or a peer-class policy for remote tool callers. [ADR-017:27-40,240-270; ADR-049:40-55]

This proposal defines a runtime-owned agent process abstraction, a provider boundary, and a single tool-dispatch protocol, with the lifecycle operations entering through the standard pack surface.

The agent process abstraction below is designed as the substrate's native process model, and this ADR is its design seed: the runtime-owned agent table is the substrate's process table, the comm system already cited above is its IPC, and the session pack's checkpoint/transcript storage is a process's suspend-and-resume state. Supervision of the runtime process that hosts these agent records belongs to the machine's supervisor tier, not to this runtime itself — this ADR designs the process model, and that model is realized only when this runtime, not a host init system, owns running agents in production. The individual primitives composed here — a durable process record with a lifecycle, checkpoint-based suspension, supervised restart, and capability attenuation at dispatch — are established operating-systems and durable-execution practice, not inventions of this ADR; the contribution claimed is their composition over khive's existing pack, session, comm, and gate surfaces, and the specific points that practice leaves unsettled for agent processes — where the restart boundary sits, how resumption avoids re-executing nondeterministic effects, and how authority behaves across time — are decided explicitly below (the restart-boundary row and checkpoint-purity rule in §1, and the authority-across-time rule under "Actor provenance").

## Decision

### 1. Process model

An agent is a runtime-owned process record and is not a pack. The runtime owns the agent table because the record represents execution lifecycle, provider binding, actor provenance, and resumable state rather than additive pack vocabulary or handlers. [ADR-017:27-40,79-106,240-270; ADR-049:40-55]

The lifecycle operations, however, enter through the standard pack surface, because every top-level operation must have a pack owner and a registry dispatch path. [ADR-003, "New verbs without packs"; ADR-017:638-645] A dedicated agent pack registers the verbs `agent.spawn`, `agent.resume`, `agent.kill`, `agent.suspend`, and `agent.observe` with the verb registry, so these operations participate in request parsing, discovery, collision handling, and gate dispatch exactly as every other verb does, under ADR-023's pack verb surface and visibility rules. The pack owns the wire surface; the runtime owns the table. The pack's handlers operate on the runtime-owned agent table through a runtime-provided accessor, and the process record itself remains runtime state, not pack state. [ADR-023:65-109]

#### Persistent process record

The runtime-owned agent table is the durable process record; it is distinct from the session pack's checkpoint/transcript storage, described immediately below. Each row carries: `agent_id` (immutable, assigned at `agent.spawn`), `state`, `terminal_reason` (nullable), `provider`, `provider_session_id` (nullable, provider-native continuity key, passed only to the provider adapter), `checkpoint_session_id` (nullable, the khive session-note identifier of the record's checkpoint artifact), `checkpoint_cursor` (nullable, the position of the last message captured in that checkpoint), `owner_actor` (see below), `owner_peer_class` (immutable snapshot, see below), `owner_write_namespace` and `owner_visible_namespaces` (immutable owner mapping-context snapshot, see below), `spawn_fingerprint` (immutable, see below), `spawned_at`, `state_changed_at`, and `idempotency_key` (nullable).

`spawn_fingerprint` is a canonical digest of the spawn's complete argument set — `provider`, `task`, `provider_session_id`, and `checkpoint_session_id` — computed once at first acceptance and never recomputed. Normalization is fixed: the arguments are serialized as a single canonical JSON object with those keys in that order, absent optional parameters omitted entirely, string values in UTF-8, and the serialization digested with the runtime's standard content hash. `idempotency_key` itself is excluded — it is the lookup key of the replay pair, not part of the compared content.

For a spawn arriving over an ADR-137-mapped connection, `owner_write_namespace` and `owner_visible_namespaces` are captured from the same atomic mapping snapshot that resolved `owner_peer_class` — the frame token's write namespace and visible namespace set — so the record's class ceiling and data-scope ceiling come from one consistent read. For a spawn arriving over native in-process or Unix-socket dispatch, both fields carry the distinguished `native` context marker: such a record's namespace semantics are the existing attribution-only namespace model governed by the gate [ADR-007], and the mapping-context rule under "Actor provenance" applies only to mapped classes.

At `agent.spawn`, the runtime enforces that at most one non-terminal process record binds a given `(provider, provider_session_id)` pair: a spawn naming a pair already held by a non-terminal record is rejected with a validation error naming the holding record. ADR-083's non-uniqueness for stored session notes is unchanged — multiple checkpoint or transcript artifacts may legitimately reference one provider-native session [ADR-083:199-212]; the constraint here is on live process records, and it is what makes the runtime's exclusive ownership of a provider session's lifetime (§2) well-defined. While a record is `suspended` it remains non-terminal and retains its pair binding, so no second record can claim the same provider session.

Agent checkpoint and transcript material uses the existing session surfaces unchanged: `session.store` persists checkpoint content, and `session.resume` restores it by the checkpoint's khive record identifier — the `checkpoint_session_id` above — exactly as ADR-083 defines that verb. The lifecycle transition itself is `agent.resume` (§1, Verb surface): the agent pack's handler consumes the session surface's restore path internally, and ADR-083's public contract for `session.resume` — an Assertive fetch of one stored session note — is not reinterpreted as a lifecycle control and is not amended by this ADR. Checkpoint restoration is a pure read of stored records: it reconstructs history from the checkpoint artifact and never re-issues a model call or re-executes a tool effect the checkpoint records — each recorded effect happened exactly once, in the run that recorded it, and a restore that replayed effects would turn resumption into re-execution. `provider_session_id` is never used to select a khive record: it is an external identifier, not unique across stored records, and it flows only to the provider adapter's continuity path. [ADR-083:145-175,199-212] The pair `checkpoint_session_id`/`checkpoint_cursor` is written atomically when a checkpoint lands: a checkpoint write that fails leaves both fields unchanged and surfaces as the outcome of the operation that required it — most concretely, a suspend whose checkpoint write fails fails the suspend (the record stays `running` with its previous restorable state intact). A checkpoint written at an ordinary message-yield boundary that fails is logged and retried at the next boundary; the record's fields keep naming the last checkpoint that actually landed.

Two constraints travel with this checkpoint contract regardless of provider. First, when the underlying model provider supports server-side session continuity, the provider-native session identifier is carried inside the checkpoint record as an opaque value: the runtime persists and forwards it unexamined, and only the checkpoint record's own fields are meaningful to the runtime — the identifier's internal shape is never interpreted. Second, a provider-side resume is not guaranteed to replay context faithfully: some providers collapse what they replay on resume (for instance, honoring only the final message of a prompt rather than restating the full conversation verbatim), so the checkpoint record, never the provider's resumed state, is the source of truth for reconstructing an agent's history; a caller reconstructing state after a resume reads it from the checkpoint record, and never infers it from whatever the provider chose to replay.

#### Observation surface

Agent-process state has exactly one canonical observation surface: the runtime-owned agent table above, read through `agent.observe` (ADR-016 request-DSL conventions). Existing host-level orchestration tooling may keep its own job or run views for its own bookkeeping, but such views are convenience mirrors, never a second source of truth — the same no-second-truth discipline this system's operations layer already applies to supervisor state. The process-record fields enumerated above are a versioned contract: evolution is additive only, a field is never removed or repurposed, so a caller built against today's `agent.observe` output does not need to track a breaking schema change tomorrow.

#### Actor provenance

An agent record's `agent_id` is process identity: an opaque, immutable handle assigned at `agent.spawn`, used to address the record for `agent.kill`/`agent.suspend`/`agent.observe`. It is never presented to the gate or to comm as an authenticated actor.

`owner_actor` is the authenticated actor context under which the runtime dispatches every verb the agent's tool calls trigger. Its source is fixed: `owner_actor` is bound, at `agent.spawn` time, to the `ActorRef` the dispatch seam already resolved for the _calling_ request — the same per-request identity every other in-process caller carries through the existing dispatch token — never a value the runtime derives from the agent record, the run id, or any field the agent process itself can influence. Every verb call the agent's dispatcher issues on the process's behalf propagates `owner_actor` through that same existing dispatch-token path unchanged. [ADR-007:277-292,527-557]

The strength of that binding is the strength of the ingress principal behind it, and the two ingress paths differ. On the remote path, the calling connection's actor is assigned by ADR-137's server-side node mapping, which a caller cannot self-assert; `owner_actor` is therefore bound to a verified principal, and the lifecycle authorizer below is a real cross-principal boundary. On the native local path, the operating-system principal is the peer UID, and actor labels over one socket are attribution rather than authenticated identity [`crates/khive-runtime/src/daemon.rs:387-400,417-422` at commit `9442ec2c5`]; every same-UID native caller is one trust domain, so within that domain the authorizer's actor-equality check defends against accidental cross-actor operation, not against a hostile same-UID process. Security-grade multi-actor lifecycle isolation between mutually untrusted parties therefore exists today only across ADR-137-mapped ingress, and this ADR deliberately does not claim it for same-UID native callers; a verified per-actor binding on the native path would be a separate decision.

The record additionally stores `owner_peer_class`: for a spawn arriving over an ADR-137-mapped connection, the peer class that mapping resolved at `agent.spawn` time, captured as an immutable snapshot on the process record precisely because the agent's later tool calls can outlive that connection. A spawn arriving over native in-process or Unix-socket dispatch is not a mapped TCP peer; its record carries the distinguished class `native`, whose allowlist is unrestricted at the transport tier — verb-level authorization for such records is governed by the gate alone (ADR-018), and the snapshot/current-mapping intersection below applies only to mapped classes.

Every subsequent tool-dispatch call the agent's dispatcher issues propagates `owner_peer_class` alongside `owner_actor` through the same dispatch-token path (§3), so an asynchronous continuation reached after the originating connection has closed still carries the class it was spawned under. `owner_peer_class` is a ceiling, never a standing grant independent of the actor: at every dispatch (§3) the gate also resolves `owner_actor`'s current mapped class through ADR-137's by-actor lookup, and enforces the intersection of the two allowlists — the record's snapshot and the actor's present mapping — which is ADR-137's defined evaluation of "the more restrictive of two classes." If an operator revokes or narrows `owner_actor`'s mapping after spawn, every later dispatch for that agent is denied or narrowed accordingly; if the actor resolves to no current class, or to conflicting classes, resolution fails closed and the dispatch is denied. The snapshot can never grant access the actor's current mapping no longer allows. [ADR-137, "Peer classes and dispatch enforcement"]

The same discipline governs data scope. At `agent.resume` and at every dispatch the agent's dispatcher issues for a mapped-class record, the runtime derives the effective data scope deterministically from exactly two inputs — the record's stored mapping-context snapshot and `owner_actor`'s current mapping — never from the resume caller's own frame context, and never from the closed initiating frame beyond what the snapshot recorded. The effective visible namespace set is the intersection of the stored `owner_visible_namespaces` and the current mapping's visible namespace set. The effective write namespace is the stored `owner_write_namespace` only when the current mapping's write namespace equals it; when the two differ, no write namespace is in scope and every write-bearing dispatch for the record is denied until an operator restores the mapping or the owner spawns a fresh record under the current one. Resolution fails closed on ambiguity: if `owner_actor` currently resolves to more than one mapping whose namespace tuples differ — including two mappings with the same actor and the same class — the current context is ambiguous and the dispatch is denied; only an actor whose current mappings agree on one namespace tuple yields a usable context. The snapshot can never widen scope beyond the current mapping, and the current mapping can never widen scope beyond the snapshot. A `native`-class record carries the distinguished native context instead (§1, Persistent process record) and is governed by the gate alone.

The class rule and the data-scope rule read the operator's present state through one atomic current-owner-context read. At `agent.resume` and at every dispatch the agent's dispatcher issues for a mapped-class record, the runtime obtains, in a single consistent read, every current mapping for `owner_actor`, the resolved class definition and allowlist, and each mapping's write and visible namespace tuple; the allowlist intersection and the data-scope derivation are both evaluated against that one result. ADR-137 already requires one atomic mapping-and-class read when admitting an incoming request frame [ADR-137, "Transport identity and actor mapping"]; this rule extends the same guarantee to asynchronous continuations that run after the originating connection has closed. An implementation that resolves the current class and the current namespace tuple in two separate lookups admits a revocation race — an operator narrowing between the reads yields a dispatch evaluated under the old allowlist with the new scope, or the reverse — and does not conform. When the single consistent read cannot be obtained, the dispatch is denied, fail closed.

For a dispatch naming a mounted identifier, the same single read additionally captures the mount's current **generation** — the pinned identifier set, its catalog-entry digests, and its effect classifications, one value that every committed re-pin atomically replaces (Outbound tool-source mounts, §3) — together with the class entries as they stand at that read, so the admission decision is made wholly under one generation. Admission under one generation never carries into another: immediately before the foreign invocation itself, the dispatcher revalidates that the mount's generation still equals the one captured at admission; a re-pin committed in between makes that comparison unequal, and the dispatch is denied and logged as catalog drift, exactly as a drifted digest is. A dispatch is therefore wholly admitted and executed under the old generation, or denied and re-attempted under the new one — it can never pair an old class approval with a new pin, and a re-pin's class-entry removals take effect for every admission after its commit.

Together, the class rule and the data-scope rule above are this ADR's authority-across-time position: an authorization observed at `agent.spawn` is a recorded ceiling, never a standing grant — every later dispatch re-derives the operator's present intent and intersects it with the recorded snapshot, so a process's authority decays with revocation instead of surviving it.

Every caller of `agent.observe`, `agent.resume`, `agent.suspend`, or `agent.kill` against an existing `agent_id` — whether reached through native in-process dispatch or through the outer-ring standard-protocol edge (see §3) — is subject to one lifecycle-record authorizer before the record is loaded or changed. For `agent.observe`, `agent.suspend`, and `agent.kill`, the caller's own resolved actor must equal the record's `owner_actor`, or the caller's current mapped peer class must be a member of the operator-declared delegated-lifecycle class set — a closed list of class names configured by the operator for agent records. `agent.resume` is deliberately outside that delegated set on every path: a resume re-dispatches under the record owner's authority and derives its scope from the owner's context (§1), so only a caller whose resolved actor equals `owner_actor` may resume a record. A delegated-class caller may therefore halt or observe a process it does not own, never continue one — the same rule §3 imposes on remote continuation, so the two contracts agree by construction rather than by exception, and a delegated resume never has to answer whose authority the resumed process would run under. There is no trust ordering between classes: membership in that closed set is the entire delegation rule for the three delegable verbs, a caller whose class is absent from the set is denied, and a caller whose actor resolves to no current class fails closed. A caller can never substitute a self-asserted identity for `owner_actor`, and a caller failing this check receives a structured denial — naming the denied lifecycle verb and the record's `owner_actor` reference, never the denying caller's own identity — before the record is loaded or its state changes. This authorizer is distinct from, and applies in addition to, the tool-call peer-class gate in §3, which governs verbs the agent itself dispatches rather than access to the agent's own lifecycle record.

### 2. Provider trait

The runtime defines a provider trait whose first-class local slot is an on-device lattice inference engine. [ADR-042:61-71]

The trait also supports plain API providers that produce model responses through a network API, and it supports externally hosted coding-agent providers only as stripped transports: native tool execution is disabled at the provider, and model interaction returns to the runtime, which remains responsible for tools, capability checks, audit context, and result delivery. [ADR-023:86-147,300-306]

#### Runtime-owned adapter contract

Every provider adapter, local or remote, is a runtime-owned worker, not a caller-blocking call: a blocking generation call (most concretely, the on-device local engine) runs on a runtime-owned worker rather than on the caller's own execution context, so a slow or stuck generation cannot block the dispatcher.

The runtime, not any individual provider adapter, owns queueing and fairness across concurrent agent processes sharing one provider slot, owns each provider session's lifetime (creation, reuse across rounds via `provider_session_id`, and teardown on the owning record's terminal transition — well-defined because at most one non-terminal record binds a provider session, §1), and owns cancellation delivery: an `agent.kill` or `agent.suspend` on the owning agent record is the runtime's signal to the worker to stop generation, not a request the provider adapter can defer or ignore. `agent.kill` tears the provider session down; `agent.suspend` releases the worker capacity, while whether the provider-native session is closed or retained across a suspend is adapter-specific and observable only through the record's continuation behavior, never through a second claimant, since the suspended record keeps its pair binding (§1).

A provider adapter that produces incremental output internally (a pull-shaped API, or a subprocess reading its stdout) is adapted to the runtime's push-shaped event delivery by the runtime, not by the provider: the adapter's own idiom stays behind the trait boundary, and every provider looks the same to the process record above it.

Every provider adapter reports exactly one terminal outcome per run — success or a classified failure — through a single terminal-outcome path that every consumer of the run reads; a provider that separately signals success on one channel and failure on another (for example, a buffered result payload that carries an unread error flag) is not a conforming adapter, and the runtime's own `terminal` lifecycle transition (§1) is driven by that one path.

Model selection within the local lattice slot is a separately scoped refinement, decided after this adapter contract, not a precondition for it.

#### Session-subscription providers

The runtime accepts the reduced utilization of session-subscription providers because they are billing-shaped transports rather than dedicated inference capacity; this utilization cost is a transport trade-off accepted by this ADR without further gating.

Every model-proposed tool call enters the substrate dispatcher, because one dispatch entry is a physical topology requirement rather than a provider policy preference. [ADR-017:164-175,240-270; ADR-049:59-65]

### 3. Tool dispatch protocol

The execution path is `model-proposed verb call -> substrate dispatcher -> result`. [ADR-017:164-175; ADR-049:59-65]

The dispatcher authenticates the agent's runtime context using `owner_actor` (§1), checks its capability scope, invokes the selected verb, and returns the resulting value or error through the provider transport. [ADR-017:164-175; ADR-023:86-147]

#### Native and foreign entry paths

An owned agent's tool calls enter khive through the native dispatch entry — in-process dispatch or, for a remote owned-agent host, ADR-137's native frame protocol — and never through a standard-protocol wrapper; a foreign, externally hosted agent enters only through ADR-137's gated outer-ring standard-protocol edge adapter. Both paths converge at the same substrate dispatcher before policy and verb execution, so neither path can bypass the peer-class gate below by choosing a different entry.

On the remote native path, owner identity propagates by equality, never by transmission. ADR-137 mints a frame's context solely from the connecting node's server-side mapping and rejects frame-supplied actor context, so a remote host cannot forward `owner_actor` in a frame and this ADR does not ask it to. Instead: a remote host may spawn only records whose `owner_actor` is the actor its own mapping resolves — which is automatic, since `agent.spawn` binds `owner_actor` from the calling request's resolved identity (§1) — and at every later agent-issued dispatch or lifecycle continuation arriving over ADR-137 frames, the dispatcher requires the connection's mapping-resolved actor to equal the record's `owner_actor`; a mismatch denies that dispatch, fail closed. Continuation here means `agent.resume` and the dispatches a resumed loop issues — the verbs that run under the owner's authority; the caller-issued halting and observation verbs (`agent.observe`, `agent.suspend`, `agent.kill`) are not continuations and remain governed solely by §1's lifecycle-record authorizer, which is how a remote delegated-class caller may halt or observe a record it does not own while never continuing one. When the actors are equal, the mapping-context rule in §1 then derives the dispatch's data scope from the record's stored snapshot and the actor's current mapping, so a continuation carries neither the closed initiating frame's scope nor the continuing connection's own frame scope. A remote host whose mapped actor differs from a record's owner therefore cannot continue that record at all. A server-minted continuation credential bound to the agent record — which would let a differently-mapped host continue an owned record — is a named possible future mechanism, not defined here; until such a mechanism is specified with its own revocation contract, actor equality is the only remote continuation identity.

A remote host's agent-context frames bind to their record through a server-owned **record attachment**, never through frame content. When `agent.spawn`, or an owner `agent.resume`, is admitted over a native connection, the server creates an attachment binding that connection to exactly that process record and returns its opaque attachment reference in the operation's response. The reference is connection-scoped and non-transferable, and it selects a record without asserting any identity — the frame's actor remains solely the connection's mapping-resolved actor, so the attachment is a routing binding, not a credential. A connection MAY hold attachments to several distinct records, with at most one live attachment per record per connection; every subsequent frame carrying a tool call or continuation on a record's behalf names exactly one attachment reference, and the server resolves all record context — the snapshot ceiling, data scope, audit attribution, and mounted-target reachability — from that attachment alone. A frame naming no attachment is an ordinary ADR-137 request: it carries no record context and cannot reach mounted identifiers. A frame naming an unknown, expired, or other-connection attachment is denied, fail closed. Attachments end with their connection — for a running record this is the live-attachment disconnect that transitions it to `abandoned` (§1) — and a reconnecting host obtains a new attachment only through a new owner `agent.resume`, whose admission re-runs the actor-equality check and the atomic current-owner-context read before any dispatch. [ADR-137, "Transport identity and actor mapping"]

#### Peer-class gate at the shared dispatch seam

This ADR adopts ADR-137's per-peer-class allowlist mechanism as the capability-scoping decision for every tool call this runtime dispatches, rather than leaving the policy to a future ADR: for a live TCP or outer-ring caller the dispatcher resolves the calling peer's mapped class exactly as ADR-137's "Peer classes and dispatch enforcement" section defines; for a tool call the runtime itself issues on an agent's behalf, the dispatcher uses the `owner_actor`/`owner_peer_class` resolution defined in §1, which already re-derives the live mapping rather than trusting a stale snapshot alone. Either path applies the resolved class's closed dispatch-target allowlist before the selected target executes. [ADR-137, "Peer classes and dispatch enforcement"]

The gate is default-deny: an unmapped peer, or a peer whose class allowlist does not name the requested dispatch target, is denied before dispatch, with no implicit fallback class. The gate applies at the one shared parsed-operation seam this runtime's dispatcher uses for every execution mode — a single tool call, a parallel batch, and a chain — so no execution mode can reach a dispatch target its peer class does not allow; a provider transport cannot bypass the gate by advertising a native tool, because native tool execution is disabled for every provider under the stripped-transport contract (§2). [ADR-137, "Peer classes and dispatch enforcement"]

The denial's response shape depends on which of the two entry paths carried the denied operation, and the split is explicit:

- For a tool call the runtime's agent-loop dispatcher issues on a process record's behalf, a denial is a visible tool result, never an exception: the dispatcher returns a denied-tool result carrying the denying peer class and the denied dispatch target, appended to the run's history exactly as any other tool result would be, so the model can observe and adapt to the denial rather than the run terminating silently or with an unstructured error.
- For a parsed operation a live caller submits itself over ADR-137's TCP transport or outer-ring edge adapter, the denial keeps ADR-137's wire contract unchanged: the request-terminal wire error `peer_class_denied` [ADR-137, "Wire error taxonomy"]. This ADR does not amend that contract.

The translating component is the agent-loop dispatcher itself: when a loop-issued tool call is denied at the shared seam, that dispatcher — not the wire transport, not the provider adapter — converts the gate's denial into the denied-tool history result. The wire error never appears in a model transcript, and the history-result shape never replaces the wire error for a live wire caller. Both shapes record the same audit event, and every dispatch, allowed or denied, on either path, is attributed in the audit trail to the path's own resolved principal. A tool call the agent-loop dispatcher issues on a process record's behalf is attributed to the record's `owner_actor` (§1) and the resolved effective class. A parsed operation a live caller submits itself — over ADR-137's TCP transport, the outer-ring edge adapter, or native dispatch — has no process record and therefore no `owner_actor`; it is attributed to the actor and class the server itself resolved for that caller: the mapping-resolved frame actor for ADR-137 ingress [ADR-137, "Transport identity and actor mapping"], or the dispatch-seam-resolved actor of §1's native trust domain for native callers. Neither path ever attributes to a self-asserted identity from the calling transport.

#### Outbound tool-source mounts

ADR-137 deliberately defers the outbound half of its interop edge to this ADR, because outbound tool calls share this runtime's dispatcher seam. The contract is:

- **Registration.** An outbound mount is an operator-registered configuration record naming the external standard-protocol tool server, its transport, and its credential by reference (an environment or configuration key name, never an inline credential value). Mounts are registered configuration, never something an agent or a model response can create. Registration additionally discovers the foreign server's tool catalog, validates it, and **pins** it: the persisted mount record carries the exact set of canonical mounted-tool identifiers observed at registration time, and that pinned set — not the foreign server's live catalog — is the mount's capability surface. The pin is definitional, not merely nominal: for each pinned identifier the mount record also persists a canonical catalog-entry digest, computed over the canonical serialization of the definition fields that constitute the tool's call contract — the tool's name, its declared description, and its complete input and output schema declarations as the foreign server published them at pin time. Alongside the digest, the mount record persists, per pinned identifier, an operator-authored **effect classification** from a closed two-value set — `read` or `mutating` — declared in the mount's registration configuration at pin time and re-declared at every re-pin. The runtime never infers this classification from the foreign server's prose, schemas, annotations, or any other foreign-published field; an identifier whose classification is absent is treated as `mutating`. At every dispatch of a mounted identifier, and at every re-pin, the runtime compares the foreign server's current definition of that tool against the pinned digest; a comparison that is unavailable or unequal is catalog drift. A tool the foreign server adds, renames, or re-shapes after registration is therefore unreachable until an operator explicitly re-pins the mount by a configuration update — a same-name tool whose definition has changed fails the digest comparison exactly as a renamed one fails the set membership — and a dispatch naming a tool absent from the pinned set, or failing its digest comparison, is denied and logged as catalog drift, fail closed.
- **Re-pin.** An intentional catalog update is an operator-authorized configuration update to the mount record, executed with live validation: the runtime re-discovers the foreign catalog, recomputes every canonical catalog-entry digest, and validates the new pinned set under the same naming rules as registration, then atomically replaces the pinned identifier set, its digests, and its effect classifications as one mount-record update. There is no partial re-pin, and until the replacement commits, every dispatch continues to be judged against the old pin, so a drifted tool stays denied throughout. The commit is the serialization point against dispatch admission: a dispatch admitted before the commit revalidates the mount generation immediately before its foreign invocation and is denied on inequality (§1, the atomic current-owner-context read), so no in-flight dispatch straddles the replacement. Every re-pin emits an audit record naming the authorizing operator, the mount, and the identifiers added, removed, or changed. A changed definition requires fresh class approval: at commit, every class-allowlist entry naming an identifier the re-pin removed, or whose digest or effect classification changed, is dropped from that class and audited as dropped, and the identifier becomes reachable from that class again only through a new operator class write — approval attached to one pinned contract never silently transfers to a different one.
- **Naming.** The canonical mounted-tool identifier is `<mount prefix>.<tool name>` under the mount's registered name prefix; a mounted identifier never shadows a native verb, and a registration or re-pin whose prefix collides with an existing verb namespace or mount, or whose pinned set would contain duplicate identifiers, is rejected at that registration or re-pin. A mounted-tool identifier is an internal dispatcher route — a tool target reachable only by the agent-loop dispatcher — not a registered verb: it is never resolvable through ordinary `request` or CLI verb dispatch, so ADR-016's startup-final verb registry is unaffected. [ADR-016; ADR-023]
- **Authorization.** The allowlist subject type is shared with ADR-137 as a closed **dispatch-target union**: a class allowlist entry names either a registered native verb or a canonical pinned mounted-tool identifier, and subscription topics remain ADR-137's separate allowlist domain. A class write validates every named target against that union — an entry naming neither a registered verb nor a currently pinned mounted identifier is rejected at write time — and ADR-137's snapshot/current subset-and-intersection evaluation runs over this same target universe, while ordinary `request`/CLI dispatch continues to reject mounted identifiers (Naming, above). A peer class names the specific pinned identifiers it may reach, and a class entry naming the whole mount is expanded, at the time the operator writes that class entry, into the then-pinned identifier set, persisted explicitly — a later re-pin never silently widens any class's allowlist. The same effective-class resolution as §1 applies, with the canonical pinned identifier as the value passed to the gate. A read-only peer class — one whose allowlist ADR-137 requires to contain only explicit read targets — may name a mounted identifier only when that identifier's pinned effect classification is `read`: a class write that would place a `mutating` or unclassified mounted identifier in a read-only class is rejected at write time, fail closed, and a re-pin that reclassifies an identifier away from `read` drops it from every read-only class at commit (Re-pin, above). Only tool calls issued by this runtime's dispatcher on behalf of a live agent record reach a mount; a mount is a tool source for agent processes, not a general verb surface.
- **Attribution and audit.** A mounted call executes under the calling agent's `owner_actor` and effective class, passes the same peer-class gate at the same seam, and is attributed in the audit trail exactly as a native dispatch.
- **Error translation.** A mounted server's failure returns as a classified tool-error result in the run's history (parity row 7), never as a raw foreign wire payload and never as a run-terminating exception.

An inbound edge caller (a remotely hosted agent admitted through ADR-137's gated edge adapter) receives the same capability scoping as an in-process verb call at this same seam; neither inbound nor outbound is a separate policy surface. [ADR-137, "Interop edge: inner ring and outer ring"]

### 5. Coexistence and cutover

Today, existing host-level orchestration tooling spawns and tracks agent runs at the machine level, outside any runtime-owned process record. This runtime is the plane that subsumes that role.

Both may run during the transition, and the coexistence rule is one of scope rather than precedence: for any agent process this runtime's agent table owns — one spawned through `agent.spawn` — that table is authoritative for the process's state, full stop; a host-level orchestration view of the same run is a convenience mirror (§1, Observation surface) and is never consulted to resolve a conflict with it. Host-level orchestration tooling remains free to spawn and track its own runs outside this runtime's ownership until the cutover criterion below is met.

The cutover trigger is a usage criterion, not a milestone label: this runtime rather than host-level orchestration tooling owns running agents in production only once that ownership is exercised daily rather than merely implemented. Before that trigger, this ADR's mechanics may be implemented and acceptance-tested without yet being the load-bearing path for a production agent process, consistent with the sequencing stated below.

## Non-goals and sequencing

This ADR does not change any existing client surface, the public client protocol, or any existing pack's verb surface; the agent pack is additive, and the runtime design target sits above the pack registry. Implementation proceeds paper-first: this ADR lands before any client-facing code changes depend on it, and the durable agent-table, provider-adapter, and peer-class-gate mechanics above are each implemented and acceptance-tested (per the parity table's Adopt rows and the two Defer rows' named gates) before any product surface advertises agent-process capability to a caller outside this runtime's own operator context.

## Consequences

The runtime gains a durable ownership point for agent lifecycle and actor provenance, while the lifecycle wire surface stays inside the standard pack model — an additive agent pack rather than an expansion of what packs are. [ADR-017:27-40,240-270; ADR-003, "New verbs without packs"]

Session continuity remains compatible with existing session semantics: `session.resume` keeps its khive-record-identifier contract, provider-native identifiers stay behind the provider adapter, and stored session notes remain free to reference one provider session more than once. [ADR-083:145-175,199-212]

The single dispatcher creates one place to apply capability checks and to connect ordinary verbs and mounted outbound tool sources. [ADR-017:164-175; ADR-137, "Peer classes and dispatch enforcement"]

Providers that previously combined inference and native tool execution must operate without their native tool path when hosted by this runtime (§2).

Subscription-based coding-agent transports may be used below their nominal capacity, and that utilization cost is accepted by this decision (§2).

The liveness-watchdog timing and the per-provider native-tool restriction mechanics remain refinement items with a named owner and gate (parity table rows 14 and 19); every other lifecycle, provider-adapter, and dispatch-protocol decision in §§1-3 is normative as written.

## Alternatives considered

### Model every agent as a pack

This alternative is rejected because packs are additive vocabulary and handler bundles, whereas a process record is runtime-owned execution state with a lifecycle and a provider binding. The chosen design keeps the record in the runtime and the wire surface in a pack, rather than collapsing either into the other. [ADR-017:27-40,128-175; ADR-023:65-85]

### Register the lifecycle operations outside the pack registry

This alternative is rejected because every top-level operation must have a pack owner to participate in parsing, discovery, collision handling, and gate dispatch; a kernel-side verb registry parallel to the pack registry would duplicate that machinery and require amending the accepted architecture for no capability the agent pack cannot provide. [ADR-003, "New verbs without packs"; ADR-017:638-645]

### Resume through the provider-native session identifier

This alternative is rejected because `provider_session_id` is an external identifier that is not a khive record identifier and is not unique across stored records; selecting a checkpoint with it is ambiguous by contract. The khive checkpoint identifier selects the record; the provider identifier keys only provider-side continuity. [ADR-083:145-175,199-212]

### Let every provider execute its native tools

This alternative is rejected because provider-native tool paths would create execution routes outside the shared dispatcher and capability boundary. [ADR-017:164-175,240-270; ADR-137, "Peer classes and dispatch enforcement"]

### Expose external tool servers directly to providers

This alternative is rejected because an outbound tool source must be scoped and observed by the same dispatcher as a local verb (§3, Outbound tool-source mounts).

### Admit remote hosted agents to the inner runtime fabric

This alternative is rejected because remote ingress must remain at the gated standard-protocol edge. [ADR-137, "Interop edge: inner ring and outer ring"]

### Treat session-subscription transports as dedicated inference capacity

This alternative is rejected because the transport's billing shape does not guarantee that utilization can be optimized by the runtime (§2).

### Leave parity semantics as open refinement items

This alternative is rejected because leaving message-role, cancellation, cleanup, and terminal-signal semantics undecided would let conforming implementations diverge on exactly the behavior callers depend on for self-correction and safe cleanup (§4).

## Open research item

One question remains open rather than decided by this ADR: which externally hosted coding-agent transports satisfy the stripped-transport contract in §2 (native tool execution disabled, model interaction returned to the runtime) without a bespoke per-provider adapter. Owner: this ADR's provider-boundary maintainer. Gate: a published comparison of candidate transports against the stripped-transport contract, before a second externally hosted provider (beyond the first reference implementation) ships in this runtime.
