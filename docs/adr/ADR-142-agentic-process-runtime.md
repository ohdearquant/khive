# ADR-142: Agentic Process Runtime

- **Status:** Proposed
- **Date:** 2026-08-03

## Context

khive packs contribute vocabulary and handlers, while the runtime composes their contributions into a coherent dispatch surface. [ADR-017:27-40,164-175; ADR-023:65-85]

The warm daemon already owns a long-lived runtime and a `VerbRegistry`, which provides the appropriate execution host for process records that must outlive one model response. [ADR-049:40-55,59-65]

The public session surface stores continuity metadata, including `provider` and `provider_session_id`, and exposes `session.store` and `session.resume`. `session.resume` selects a stored session note by its khive record identifier; `provider_session_id` is an external, provider-native identifier that is not a khive record identifier and is not unique across stored records. [ADR-083:80-99,145-175,199-212]

The comm model already distinguishes an actor identity from a message payload and carries that identity through runtime request context. [ADR-057:120-152; ADR-063:95-132]

On the daemon's native local path, the operating-system peer UID is the authenticated principal, and many actor identities over one socket is the accepted design: the actor label is per-request attribution, not an independently authenticated identity. [ADR-096; `crates/khive-runtime/src/daemon.rs:387-400,417-422` at commit `9442ec2c5`]

An on-device lattice inference seam is an established direction for local inference, although the cited native rerank integration is explicitly deferred rather than evidence that a general agent provider exists today. [ADR-042:18-38,61-71]

Today's runtime composes packs through a registry and accepts per-request identity only at its dispatch boundary; no current source defines a durable agent-process record, a provider abstraction, or a peer-class policy for remote tool callers. [ADR-017:27-40,240-270; ADR-049:40-55]

This proposal defines a runtime-owned agent process abstraction, a provider boundary, and a single tool-dispatch protocol, with the lifecycle operations entering through the standard pack surface.

The agent process abstraction below is designed as the substrate's native process model, and this ADR is its design seed: the runtime-owned agent table is the substrate's process table, the comm system already cited above is its IPC, and the session pack's checkpoint/transcript storage is a process's suspend-and-resume state. Supervision of the runtime process that hosts these agent records belongs to the machine's supervisor tier, not to this runtime itself — this ADR designs the process model, and that model is realized only when this runtime, not a host init system, owns running agents in production.

## Decision

### 1. Process model

An agent is a runtime-owned process record and is not a pack. The runtime owns the agent table because the record represents execution lifecycle, provider binding, actor provenance, and resumable state rather than additive pack vocabulary or handlers. [ADR-017:27-40,79-106,240-270; ADR-049:40-55]

The lifecycle operations, however, enter through the standard pack surface, because every top-level operation must have a pack owner and a registry dispatch path. [ADR-003, "New verbs without packs"; ADR-017:638-645] A dedicated agent pack registers the verbs `agent.spawn`, `agent.resume`, `agent.kill`, `agent.suspend`, and `agent.observe` with the verb registry, so these operations participate in request parsing, discovery, collision handling, and gate dispatch exactly as every other verb does, under ADR-023's pack verb surface and visibility rules. The pack owns the wire surface; the runtime owns the table. The pack's handlers operate on the runtime-owned agent table through a runtime-provided accessor, and the process record itself remains runtime state, not pack state. [ADR-023:65-109]

#### Persistent process record

The runtime-owned agent table is the durable process record; it is distinct from the session pack's checkpoint/transcript storage, described immediately below. Each row carries: `agent_id` (immutable, assigned at `agent.spawn`), `state`, `terminal_reason` (nullable), `provider`, `provider_session_id` (nullable, provider-native continuity key, passed only to the provider adapter), `checkpoint_session_id` (nullable, the khive session-note identifier of the record's checkpoint artifact), `checkpoint_cursor` (nullable, the position of the last message captured in that checkpoint), `owner_actor` (see below), `owner_peer_class` (immutable snapshot, see below), `spawned_at`, `state_changed_at`, and `idempotency_key` (nullable).

At `agent.spawn`, the runtime enforces that at most one non-terminal process record binds a given `(provider, provider_session_id)` pair: a spawn naming a pair already held by a non-terminal record is rejected with a validation error naming the holding record. ADR-083's non-uniqueness for stored session notes is unchanged — multiple checkpoint or transcript artifacts may legitimately reference one provider-native session [ADR-083:199-212]; the constraint here is on live process records, and it is what makes the runtime's exclusive ownership of a provider session's lifetime (§2) well-defined. While a record is `suspended` it remains non-terminal and retains its pair binding, so no second record can claim the same provider session.

Agent checkpoint and transcript material uses the existing session surfaces unchanged: `session.store` persists checkpoint content, and `session.resume` restores it by the checkpoint's khive record identifier — the `checkpoint_session_id` above — exactly as ADR-083 defines that verb. The lifecycle transition itself is `agent.resume` (§1, Verb surface): the agent pack's handler consumes the session surface's restore path internally, and ADR-083's public contract for `session.resume` — an Assertive fetch of one stored session note — is not reinterpreted as a lifecycle control and is not amended by this ADR. `provider_session_id` is never used to select a khive record: it is an external identifier, not unique across stored records, and it flows only to the provider adapter's continuity path. [ADR-083:145-175,199-212] The pair `checkpoint_session_id`/`checkpoint_cursor` is written atomically when a checkpoint lands: a checkpoint write that fails leaves both fields unchanged and surfaces as the outcome of the operation that required it — most concretely, a suspend whose checkpoint write fails fails the suspend (the record stays `running` with its previous restorable state intact). A checkpoint written at an ordinary message-yield boundary that fails is logged and retried at the next boundary; the record's fields keep naming the last checkpoint that actually landed.

Two constraints travel with this checkpoint contract regardless of provider. First, when the underlying model provider supports server-side session continuity, the provider-native session identifier is carried inside the checkpoint record as an opaque value: the runtime persists and forwards it unexamined, and only the checkpoint record's own fields are meaningful to the runtime — the identifier's internal shape is never interpreted. Second, a provider-side resume is not guaranteed to replay context faithfully: some providers collapse what they replay on resume (for instance, honoring only the final message of a prompt rather than restating the full conversation verbatim), so the checkpoint record, never the provider's resumed state, is the source of truth for reconstructing an agent's history; a caller reconstructing state after a resume reads it from the checkpoint record, and never infers it from whatever the provider chose to replay.

#### Observation surface

Agent-process state has exactly one canonical observation surface: the runtime-owned agent table above, read through `agent.observe` (ADR-016 request-DSL conventions). Existing host-level orchestration tooling may keep its own job or run views for its own bookkeeping, but such views are convenience mirrors, never a second source of truth — the same no-second-truth discipline this system's operations layer already applies to supervisor state. The process-record fields enumerated above are a versioned contract: evolution is additive only, a field is never removed or repurposed, so a caller built against today's `agent.observe` output does not need to track a breaking schema change tomorrow.

#### Actor provenance

An agent record's `agent_id` is process identity: an opaque, immutable handle assigned at `agent.spawn`, used to address the record for `agent.kill`/`agent.suspend`/`agent.observe`. It is never presented to the gate or to comm as an authenticated actor.

`owner_actor` is the authenticated actor context under which the runtime dispatches every verb the agent's tool calls trigger. Its source is fixed: `owner_actor` is bound, at `agent.spawn` time, to the `ActorRef` the dispatch seam already resolved for the _calling_ request — the same per-request identity every other in-process caller carries through the existing dispatch token — never a value the runtime derives from the agent record, the run id, or any field the agent process itself can influence. Every verb call the agent's dispatcher issues on the process's behalf propagates `owner_actor` through that same existing dispatch-token path unchanged. [ADR-007:277-292,527-557]

The strength of that binding is the strength of the ingress principal behind it, and the two ingress paths differ. On the remote path, the calling connection's actor is assigned by ADR-137's server-side node mapping, which a caller cannot self-assert; `owner_actor` is therefore bound to a verified principal, and the lifecycle authorizer below is a real cross-principal boundary. On the native local path, the operating-system principal is the peer UID, and actor labels over one socket are attribution rather than authenticated identity [`crates/khive-runtime/src/daemon.rs:387-400,417-422` at commit `9442ec2c5`]; every same-UID native caller is one trust domain, so within that domain the authorizer's actor-equality check defends against accidental cross-actor operation, not against a hostile same-UID process. Security-grade multi-actor lifecycle isolation between mutually untrusted parties therefore exists today only across ADR-137-mapped ingress, and this ADR deliberately does not claim it for same-UID native callers; a verified per-actor binding on the native path would be a separate decision.

The record additionally stores `owner_peer_class`: for a spawn arriving over an ADR-137-mapped connection, the peer class that mapping resolved at `agent.spawn` time, captured as an immutable snapshot on the process record precisely because the agent's later tool calls can outlive that connection. A spawn arriving over native in-process or Unix-socket dispatch is not a mapped TCP peer; its record carries the distinguished class `native`, whose allowlist is unrestricted at the transport tier — verb-level authorization for such records is governed by the gate alone (ADR-018), and the snapshot/current-mapping intersection below applies only to mapped classes.

Every subsequent tool-dispatch call the agent's dispatcher issues propagates `owner_peer_class` alongside `owner_actor` through the same dispatch-token path (§3), so an asynchronous continuation reached after the originating connection has closed still carries the class it was spawned under. `owner_peer_class` is a ceiling, never a standing grant independent of the actor: at every dispatch (§3) the gate also resolves `owner_actor`'s current mapped class through ADR-137's by-actor lookup, and enforces the intersection of the two allowlists — the record's snapshot and the actor's present mapping — which is ADR-137's defined evaluation of "the more restrictive of two classes." If an operator revokes or narrows `owner_actor`'s mapping after spawn, every later dispatch for that agent is denied or narrowed accordingly; if the actor resolves to no current class, or to conflicting classes, resolution fails closed and the dispatch is denied. The snapshot can never grant access the actor's current mapping no longer allows. [ADR-137, "Peer classes and dispatch enforcement"]

Every caller of `agent.observe`, `agent.resume`, `agent.suspend`, or `agent.kill` against an existing `agent_id` — whether reached through native in-process dispatch or through the outer-ring standard-protocol edge (see §3) — is subject to one lifecycle-record authorizer before the record is loaded or changed: the caller's own resolved actor must equal the record's `owner_actor`, or the caller's current mapped peer class must be a member of the operator-declared delegated-lifecycle class set — a closed list of class names configured by the operator for agent records. There is no trust ordering between classes: membership in that closed set is the entire delegation rule, a caller whose class is absent from the set is denied, and a caller whose actor resolves to no current class fails closed. A caller can never substitute a self-asserted identity for `owner_actor`, and a caller failing this check receives a structured denial — naming the denied lifecycle verb and the record's `owner_actor` reference, never the denying caller's own identity — before the record is loaded or its state changes. This authorizer is distinct from, and applies in addition to, the tool-call peer-class gate in §3, which governs verbs the agent itself dispatches rather than access to the agent's own lifecycle record.

### 2. Provider trait

The runtime defines a provider trait whose first-class local slot is an on-device lattice inference engine. [ADR-042:61-71]

The trait also supports plain API providers that produce model responses through a network API, and it supports externally hosted coding-agent providers only as stripped transports: native tool execution is disabled at the provider, and model interaction returns to the runtime, which remains responsible for tools, capability checks, audit context, and result delivery. [ADR-023:86-147,300-306]

#### Runtime-owned adapter contract

Every provider adapter, local or remote, is a runtime-owned worker, not a caller-blocking call: a blocking generation call (most concretely, the on-device local engine) runs on a runtime-owned worker rather than on the caller's own execution context, so a slow or stuck generation cannot block the dispatcher.

The runtime, not any individual provider adapter, owns queueing and fairness across concurrent agent processes sharing one provider slot, owns each provider session's lifetime (creation, reuse across rounds via `provider_session_id`, and teardown on the owning record's terminal transition — well-defined because at most one non-terminal record binds a provider session, §1), and owns cancellation delivery: an `agent.kill` or `agent.suspend` on the owning agent record is the runtime's signal to the worker to stop generation, not a request the provider adapter can defer or ignore. `agent.kill` tears the provider session down; `agent.suspend` releases the worker capacity, while whether the provider-native session is closed or retained across a suspend is adapter-specific and observable only through the record's continuation behavior, never through a second claimant, since the suspended record keeps its pair binding (§1).

A provider adapter that produces incremental output internally (a pull-shaped API, or a subprocess reading its stdout) is adapted to the runtime's push-shaped event delivery by the runtime, not by the provider: the adapter's own idiom stays behind the trait boundary, and every provider looks the same to the process record above it.

Every provider adapter reports exactly one terminal outcome per run — success or a classified failure — through a single terminal-outcome path that every consumer of the run reads; a provider that separately signals success on one channel and failure on another (for example, a buffered result payload that carries an unread error flag) is not a conforming adapter, and the runtime's own `terminal` lifecycle transition (§1) is driven by that one path.

Model selection within the local lattice slot is a separately scoped refinement, decided after this adapter contract, not a precondition for it.

#### Session-subscription providers

The runtime accepts the reduced utilization of session-subscription providers because they are billing-shaped transports rather than dedicated inference capacity; this utilization cost is a transport trade-off accepted by this ADR without further gating.

Every model-proposed tool call enters the substrate dispatcher, because one dispatch entry is a physical topology requirement rather than a provider policy preference. [ADR-017:164-175,240-270; ADR-049:59-65]

### 3. Tool dispatch protocol

The execution path is `model-proposed verb call -> substrate dispatcher -> result`. [ADR-017:164-175; ADR-049:59-65]

The dispatcher authenticates the agent's runtime context using `owner_actor` (§1), checks its capability scope, invokes the selected verb, and returns the resulting value or error through the provider transport. [ADR-017:164-175; ADR-023:86-147]

#### Native and foreign entry paths

An owned agent's tool calls enter khive through the native dispatch entry — in-process dispatch or, for a remote owned-agent host, ADR-137's native frame protocol — and never through a standard-protocol wrapper; a foreign, externally hosted agent enters only through ADR-137's gated outer-ring standard-protocol edge adapter. Both paths converge at the same substrate dispatcher before policy and verb execution, so neither path can bypass the peer-class gate below by choosing a different entry.

On the remote native path, owner identity propagates by equality, never by transmission. ADR-137 mints a frame's context solely from the connecting node's server-side mapping and rejects frame-supplied actor context, so a remote host cannot forward `owner_actor` in a frame and this ADR does not ask it to. Instead: a remote host may spawn only records whose `owner_actor` is the actor its own mapping resolves — which is automatic, since `agent.spawn` binds `owner_actor` from the calling request's resolved identity (§1) — and at every later agent-issued dispatch or lifecycle continuation arriving over ADR-137 frames, the dispatcher requires the connection's mapping-resolved actor to equal the record's `owner_actor`; a mismatch denies that dispatch, fail closed. A remote host whose mapped actor differs from a record's owner therefore cannot continue that record at all. A server-minted continuation credential bound to the agent record — which would let a differently-mapped host continue an owned record — is a named possible future mechanism, not defined here; until such a mechanism is specified with its own revocation contract, actor equality is the only remote continuation identity.

#### Peer-class gate at the shared dispatch seam

This ADR adopts ADR-137's per-peer-class allowlist mechanism as the capability-scoping decision for every tool call this runtime dispatches, rather than leaving the policy to a future ADR: for a live TCP or outer-ring caller the dispatcher resolves the calling peer's mapped class exactly as ADR-137's "Peer classes and dispatch enforcement" section defines; for a tool call the runtime itself issues on an agent's behalf, the dispatcher uses the `owner_actor`/`owner_peer_class` resolution defined in §1, which already re-derives the live mapping rather than trusting a stale snapshot alone. Either path applies the resolved class's closed verb allowlist before the selected verb executes. [ADR-137, "Peer classes and dispatch enforcement"]

The gate is default-deny: an unmapped peer, or a peer whose class allowlist does not name the requested verb, is denied before dispatch, with no implicit fallback class. The gate applies at the one shared parsed-operation seam this runtime's dispatcher uses for every execution mode — a single tool call, a parallel batch, and a chain — so no execution mode can reach a verb its peer class does not allow; a provider transport cannot bypass the gate by advertising a native tool, because native tool execution is disabled for every provider under the stripped-transport contract (§2). [ADR-137, "Peer classes and dispatch enforcement"]

The denial's response shape depends on which of the two entry paths carried the denied operation, and the split is explicit:

- For a tool call the runtime's agent-loop dispatcher issues on a process record's behalf, a denial is a visible tool result, never an exception: the dispatcher returns a denied-tool result carrying the denying peer class and the denied verb, appended to the run's history exactly as any other tool result would be, so the model can observe and adapt to the denial rather than the run terminating silently or with an unstructured error.
- For a parsed operation a live caller submits itself over ADR-137's TCP transport or outer-ring edge adapter, the denial keeps ADR-137's wire contract unchanged: the request-terminal wire error `peer_class_denied` [ADR-137, "Wire error taxonomy"]. This ADR does not amend that contract.

The translating component is the agent-loop dispatcher itself: when a loop-issued tool call is denied at the shared seam, that dispatcher — not the wire transport, not the provider adapter — converts the gate's denial into the denied-tool history result. The wire error never appears in a model transcript, and the history-result shape never replaces the wire error for a live wire caller. Both shapes record the same audit event: every dispatch, allowed or denied, on either path, is attributed in the audit trail to the resolved `owner_actor` (§1) and the resolved peer class, never to a self-asserted identity from the calling transport.

#### Outbound tool-source mounts

ADR-137 deliberately defers the outbound half of its interop edge to this ADR, because outbound tool calls share this runtime's dispatcher seam. The contract is:

- **Registration.** An outbound mount is an operator-registered configuration record naming the external standard-protocol tool server, its transport, and its credential by reference (an environment or configuration key name, never an inline credential value). Mounts are registered configuration, never something an agent or a model response can create. Registration additionally discovers the foreign server's tool catalog, validates it, and **pins** it: the persisted mount record carries the exact set of canonical mounted-tool identifiers observed at registration time, and that pinned set — not the foreign server's live catalog — is the mount's capability surface. A tool the foreign server adds, renames, or re-shapes after registration is unreachable until an operator explicitly re-pins the mount by a configuration update; a dispatch naming a tool absent from the pinned set, or whose live definition no longer matches its pinned identity, is denied and logged as catalog drift, fail closed.
- **Naming.** The canonical mounted-tool identifier is `<mount prefix>.<tool name>` under the mount's registered name prefix; a mounted identifier never shadows a native verb, and a registration or re-pin whose prefix collides with an existing verb namespace or mount, or whose pinned set would contain duplicate identifiers, is rejected at that registration or re-pin. A mounted-tool identifier is an internal dispatcher route — a tool target reachable only by the agent-loop dispatcher — not a registered verb: it is never resolvable through ordinary `request` or CLI verb dispatch, so ADR-016's startup-final verb registry is unaffected. [ADR-016; ADR-023]
- **Authorization.** A mount's pinned tool identifiers are allowlist subjects like verbs: a peer class names the specific pinned identifiers it may reach, and a class entry naming the whole mount is expanded, at the time the operator writes that class entry, into the then-pinned identifier set, persisted explicitly — a later re-pin never silently widens any class's allowlist. The same effective-class resolution as §1 applies, with the canonical pinned identifier as the value passed to the gate. Only tool calls issued by this runtime's dispatcher on behalf of a live agent record reach a mount; a mount is a tool source for agent processes, not a general verb surface.
- **Attribution and audit.** A mounted call executes under the calling agent's `owner_actor` and effective class, passes the same peer-class gate at the same seam, and is attributed in the audit trail exactly as a native dispatch.
- **Error translation.** A mounted server's failure returns as a classified tool-error result in the run's history (parity row 7), never as a raw foreign wire payload and never as a run-terminating exception.

An inbound edge caller (a remotely hosted agent admitted through ADR-137's gated edge adapter) receives the same capability scoping as an in-process verb call at this same seam; neither inbound nor outbound is a separate policy surface. [ADR-137, "Interop edge: inner ring and outer ring"]

| 11 | Parse failure          | Adopt    | Parse failure is reported as one of two distinct classes — the response parsed but the schema rejected it, or parsing itself failed — so a caller can distinguish a provider-trouble failure from a schema-trouble failure.                                                                                                                                                                                                                                                                                      |
| 12 | Cancellation           | Adopt    | `agent.kill` (§1) is a hard stop; `agent.suspend` (§1) is a soft, checkpoint-boundary stop; a calling connection disconnecting without either is `abandoned`, a clean terminal, not a failure.                                                                                                                                                                                                                                                                                                                   |
| 13 | Cleanup                | Adopt    | Every exit path — completion, failure, kill, or abandonment — cascades to close the process's subprocess or worker handle; cleanup errors are logged and never mask the run's own terminal outcome.                                                                                                                                                                                                                                                                                                              |

| 18 | Orphan tool result     | Adopt    | A tool-result-shaped event with no matching pending tool-call record is dropped and logged as a protocol anomaly, never appended to history as if it answered a real call.                                                                                                                                                                                                                                                                                                                                       |

### 5. Coexistence and cutover

Today, existing host-level orchestration tooling spawns and tracks agent runs at the machine level, outside any runtime-owned process record. This runtime is the plane that subsumes that role.

Both may run during the transition, and the coexistence rule is one of scope rather than precedence: for any agent process this runtime's agent table owns — one spawned through `agent.spawn` — that table is authoritative for the process's state, full stop; a host-level orchestration view of the same run is a convenience mirror (§1, Observation surface) and is never consulted to resolve a conflict with it. Host-level orchestration tooling remains free to spawn and track its own runs outside this runtime's ownership until the cutover criterion below is met.

The cutover trigger is a usage criterion, not a milestone label: this runtime rather than host-level orchestration tooling owns running agents in production only once that ownership is exercised daily rather than merely implemented. Before that trigger, this ADR's mechanics may be implemented and acceptance-tested without yet being the load-bearing path for a production agent process, consistent with the sequencing stated below.

## Non-goals and sequencing

This ADR does not change any existing client surface, the public client protocol, or any existing pack's verb surface; the agent pack is additive, and the runtime design target sits above the pack registry. Implementation proceeds paper-first: this ADR lands before any client-facing code changes depend on it, and the durable agent-table, provider-adapter, and peer-class-gate mechanics above are each implemented and acceptance-tested (per the parity table's Adopt rows and the two Defer rows' named gates) before any product surface advertises agent-process capability to a caller outside this runtime's own operator context.

## Consequences

The runtime gains a durable ownership point for agent lifecycle and actor provenance, while the lifecycle wire surface stays inside the standard pack model — an additive agent pack rather than an expansion of what packs are. [ADR-017:27-40,240-270; ADR-003, "New verbs without packs"]

Session continuity remains compatible with existing session semantics: `session.resume` keeps its khive-record-identifier contract, provider-native identifiers stay behind the provider adapter, and stored session notes remain free to reference one provider session more than once. [ADR-083:145-175,199-212]

The single dispatcher creates one place to apply capability checks and to connect ordinary verbs and mounted outbound tool sources. [ADR-017:164-175; ADR-137, "Peer classes and dispatch enforcement"]

Providers that previously combined inference and native tool execution must operate without their native tool path when hosted by this runtime (§2).

Subscription-based coding-agent transports may be used below their nominal capacity, and that utilization cost is accepted by this decision (§2).

The liveness-watchdog timing and the per-provider native-tool restriction mechanics remain refinement items with a named owner and gate (parity table rows 14 and 19); every other lifecycle, provider-adapter, and dispatch-protocol decision in §§1-3 is normative as written.

## Alternatives considered

### Model every agent as a pack

This alternative is rejected because packs are additive vocabulary and handler bundles, whereas a process record is runtime-owned execution state with a lifecycle and a provider binding. The chosen design keeps the record in the runtime and the wire surface in a pack, rather than collapsing either into the other. [ADR-017:27-40,128-175; ADR-023:65-85]

### Register the lifecycle operations outside the pack registry

This alternative is rejected because every top-level operation must have a pack owner to participate in parsing, discovery, collision handling, and gate dispatch; a kernel-side verb registry parallel to the pack registry would duplicate that machinery and require amending the accepted architecture for no capability the agent pack cannot provide. [ADR-003, "New verbs without packs"; ADR-017:638-645]

### Resume through the provider-native session identifier

This alternative is rejected because `provider_session_id` is an external identifier that is not a khive record identifier and is not unique across stored records; selecting a checkpoint with it is ambiguous by contract. The khive checkpoint identifier selects the record; the provider identifier keys only provider-side continuity. [ADR-083:145-175,199-212]

### Let every provider execute its native tools

This alternative is rejected because provider-native tool paths would create execution routes outside the shared dispatcher and capability boundary. [ADR-017:164-175,240-270; ADR-137, "Peer classes and dispatch enforcement"]

### Expose external tool servers directly to providers

This alternative is rejected because an outbound tool source must be scoped and observed by the same dispatcher as a local verb (§3, Outbound tool-source mounts).

### Admit remote hosted agents to the inner runtime fabric

This alternative is rejected because remote ingress must remain at the gated standard-protocol edge. [ADR-137, "Interop edge: inner ring and outer ring"]

### Treat session-subscription transports as dedicated inference capacity

This alternative is rejected because the transport's billing shape does not guarantee that utilization can be optimized by the runtime (§2).

### Leave parity semantics as open refinement items

This alternative is rejected because leaving message-role, cancellation, cleanup, and terminal-signal semantics undecided would let conforming implementations diverge on exactly the behavior callers depend on for self-correction and safe cleanup (§4).

## Open research item

One question remains open rather than decided by this ADR: which externally hosted coding-agent transports satisfy the stripped-transport contract in §2 (native tool execution disabled, model interaction returned to the runtime) without a bespoke per-provider adapter. Owner: this ADR's provider-boundary maintainer. Gate: a published comparison of candidate transports against the stripped-transport contract, before a second externally hosted provider (beyond the first reference implementation) ships in this runtime.
