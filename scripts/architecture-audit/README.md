# Architecture audit

This standalone development tool audits an exact Git commit. It reads regular source and SQL blobs through validated local Git read commands; it does not read the working tree, run Cargo metadata, compile source, prepare SQL or change repository state.

```sh
cargo run --manifest-path scripts/architecture-audit/Cargo.toml -- \
  --repo /path/to/khive --commit FULL_40_HEX_COMMIT_OID \
  --crate khive-pack-git --crate khive-pack-brain --json
```

Omit `--crate` to select captured crate packages. The commit must be a full commit object ID; symbolic refs, abbreviations and tag objects are refused. Output records the audited commit/tree and input blob identities separately from the running tool version. Text output includes the same evidence JSON after its count summary. Relevant read, decode, manifest, reachable-source, module or classifier failures print nonempty diagnostics and exit 2. Bounds are 32 MiB for the tree inventory, 16 MiB per source blob and 256 MiB total decoded snapshot.

The production route starts only at Cargo library/binary targets, including explicit paths, conventional entries, automatic bins and required-feature provenance. It is a source union with `test=false`: known false cfg items are blanked before scanning, while platform/feature predicates retain conditional evidence. This is not compiler reachability. Unknown cfg_attr that changes cfg/path is incomplete rather than a silently chosen alternative. Out-of-line test modules and orphan files cannot become production roots through a catchall scan. A separate `test=true` source-union walk and declared/conventional integration-test roots provide test-reader evidence; its diagnostics are labeled separately and do not establish native test acceptance. `production_complete` and `test_source_complete` report the two traversals separately. An incomplete selected test walk makes the overall report incomplete and exit 2, retains positively observed production counts, and labels unobserved nonproduction assets `test-read-unknown` rather than certifying them unread. `test_read_unknown_asset_count` is separate from known test-only and unread counts. In any incomplete report, absent readers and counts are partial source evidence, not an exhaustive absence claim.

The same lexical/module resolver serves the unchanged runtime SQL policy test and this production route. Runtime policy retains its old inventory-derived crate population, compound-cfg behavior, unvisited-source fallback, error ordering, keep catalog and external-include existence handling. Production uses immutable snapshot existence, per-entry bindings and explicit roots. Loader aliases, shadows, globs, module ancestry and static include expressions are resolved conservatively. SQL loader arguments are metadata, not additional inline statements. Named macro definitions and comment/doc strings are excluded. Supported expression macros are traversed; unsupported SQL-looking opaque inputs make the result incomplete.

Count units are explicit:

- `asset_total`: regular `.sql` blobs directly in `crates/<crate>/sql/`. Nested SQL assets are outside this flat primary inventory. A verified reader of nested or other out-of-directory SQL still appears as a reader site, with its immutable asset identity, and is not silently added to the primary asset total.
- `asset_production`: distinct primary assets with a verified production reader. Repeated readers do not multiply this count; cross-crate readers credit the owning asset. Per-crate assets belong to the directory containing the asset; reader sites belong to the reading crate. Credit comes from the union of the selected crate traversals, so an unselected crate's reader does not contribute to a selected owner's production count. A production-read asset's located classifier uncertainty also appears in its owning crate's `asset_sql_diagnostics` and prevents that crate's `production_complete`, even when its readers belong to another selected crate; known asset credit is retained.
- `reader_site_count`: distinct source path/span/asset/loader identities, retaining conditional mounting and target-root provenance.
- `inline_sql_occurrences`: distinct production expression sites with a structurally proved relation target, including visible dynamic-target roles.
- `production_sql = asset_production + inline_sql_occurrences`. Test-only assets, unread assets, tableless SQL and incomplete/opaque cases are separate. Definite and conditional subtotals describe source evidence, not simultaneous compilation.

The pure SQL classifier distinguishes actual Rust format templates from ordinary SQL literals. A quoted `{table}` identifier is literal/static in ordinary SQL; it is a dynamic target only in an actual template, while escaped template braces render a literal identifier. Partial assembled relation fragments remain diagnostic evidence. The classifier recognizes relation roles and quoted/schema-qualified/dynamic identifiers, with explicit CTE and multi-statement handling. It neither proves SQL validity nor resolves schema objects. A literal is one occurrence even when it contains several statements. Included SQL asset contents are inventoried and classified without being counted again as inline source. Stable paths, byte offsets, one-based locations, roots, cfg observations and object IDs permit independent hand counting.
